# Provenance: SafeEvidence desktop shell

Admission `ADM-0006` (T36) in `docs/evidence/source_admissions.json`.

- Source: `AbdulazizShehri/MedScale` @ `5c33d77c0a82748c1fab85a9f2fd7b515145fea2`, `apps/desktop-tauri/`, Apache-2.0.
- Copied and reduced: the Tauri and Vite configuration, the capability and navigation discipline, the startup-failure path and the
  permission tests. MedScale's commands, routes, autogenerated permissions, brand assets and Tailwind are not copied.
- Tightened: `default-src 'none'` and no `'unsafe-inline'` in production, and bundling is off.
- Adapted from the donor's `src/ipc.ts` and `src/ipc.test.ts`: the reject-a-mismatched-protocol parser pattern in `src/ask-view.ts` and its test.
- SafeEvidence-written (GREENFIELD_JUSTIFIED, product-specific view; the shell is the copied part): the rest of `src/ask-view.ts`,
  `src/App.tsx`, `src/styles.css`, `src-tauri/src/ask_command.rs`. The icons are generated plain squares.

The Ask command commits through `safeevidence-proofstore` first, and shows the stored text only if the stored proof reads `COMMITTED`. No existing test tells that read from Ask's own text, because the commit binds the text's digest: a mutant that removes only the read passes every test.

## Limits

- **Key custody is on-device and has no recovery path.** The store's root key is held by the OS protector: DPAPI on Windows, Keychain on macOS, and Secret Service through the helper on Linux. Answers survive a restart. If the key is lost or wrong, the store is
  refused and its contents are kept, with no way to recover it yet. A refused open, with a wrong key or on a damaged main file, can still merge a live WAL into the main file, which changes the files. Backup, restore and rotation are not wired in. This holds invented data only.
- A store that was established and has lost or emptied its main file, or its schema, is refused, and so is a WAL with no main file, so none can be silently recreated. Removing the store directory by hand is the only way to start again.
- **Loss of the WAL can go unnoticed.** Once the main file holds a schema, a lost or damaged WAL looks like a clean store, so commits since the last checkpoint are forgotten with no warning, an invalidated answer could come back as an answer, and an old proof could read "Just committed" again. Telling them apart needs a protected anchor, which is not built. A kill alone is safe: this needs the WAL itself to be damaged.
- Each fixture digest has its own store directory, so a changed fixture starts a new store and the old one stays on disk, unused and never cleaned up.
- A crash during first install can leave a partial protector record or a `dpapi` directory with an inherited ACL. Those are refused until someone removes them by hand. A review measured this at 19 of 400 kills spread across the first open, of about 70 ms, on real DPAPI. No data is at stake in that state. A copied or restored `dpapi` directory is refused too, and no manual ACL repair has been established.
- Only Windows runs its real protector in the desktop tests. macOS has not been run through this path, and Linux reaches it only through the helper, whose real-provider tests are in its own crate. Nothing installs the helper beside the app, so on Linux the app refuses every question until
  `safeevidence-linux-keyring-helper` is placed next to its executable.
- The store has no migrations, so a schema change would refuse an existing store. `vault-identity.bin` is not secret and not protected: changing it only stops the key from being found.
- The P00 states such as `KEY_UNAVAILABLE` are not shown. Every failure to open the store reaches the view as the same `BLOCKED` with `TOOL_FAILURE`: a lost or wrong key, a damaged identity or store, a missing helper, and a second instance look alike.
- A lock file gives one running instance per data directory. A second instance refuses every question it would answer with `BLOCKED`.
- `TA-20` is not claimed. `e2e/ask_e2e.mjs` runs the Ask flow in a real WebView2 window, with real DPAPI and a real kill and restart, as the Ask subset. It has passed on a developer machine and on hosted Windows runners (first in run 42330781667, at `436208c`). In run 42328363734, on runtime 156, the browser's command line did not carry `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`, though the variable works on a developer machine with runtime 157. The cause is not known, so the `e2e` feature sets the debugging port itself. A release build refuses that feature, and nothing covers a debug build given it by hand. `e2e/ask_e2e_linux.mjs` runs the shared checks on a hosted Ubuntu runner (first passed in run 42346674671, at `9e3cfc1`), in a real WebKitGTK window with a real Secret Service, except the network log, which WebDriver does not expose. Run 42348262998 removed the CSP and granted `core:default`: all the CSP probes flipped and the refusal became "allowed". It places the helper beside the app itself, because nothing installs it yet. Its window is not incognito, because wry turns automation off for an incognito window on Linux, so nothing on Linux tests the shipped incognito setting. The restart reopens the same running keyring daemon, so keyring persistence across a daemon restart is not tested. VS-1 needs both platforms. Of the shell checklist, it covers only CSP and the capability.
  `TA-21` is not claimed: the test's network log covers this page, not the process, and T05 is not back. Native tests also use Tauri's mock runtime, which establishes no WebView privacy, OS isolation or network behaviour.
- `TA-22` is not claimed. The view is keyboard-operable with `dir="auto"` text, but has no axe or RTL snapshot run. The donor's contrast test was
  not carried over, and the new palette has no contrast check.
- A denied navigation still sends its request: a review harness on WebView2, with remote debugging on, saw `location.href` reach a local listener
  while the page stayed put. CSP has no directive for this. No route for script into the page was found, so it is not reachable today, but TA-21 must
  cover it.
- A release build must enable `custom-protocol`, or Tauri uses `devCsp` and `devUrl`. Nothing here builds a release yet.
- The proof store's rule for two committed proofs on one question is still owed. It is unreachable here, with one epoch and one grant.
- The app's Rust and npm trees are outside TA-02's SBOM, `product/deny.toml` and the TA-03 isolated run. `tools/ci/ta29_desktop_denial.py`
  checks TA-29's named clients on the three desktop targets. For the Linux target, `cargo tree -e normal` shows no `mio` or `socket2`, and the lockfile has no `zbus`,
  which moved to the separate helper.
- Tauri pulls `reqwest` and `hyper` on Android and iOS, so this shell cannot pass TA-29 on mobile as it stands.
- Native tests check CSP as configuration only. `e2e/ask_e2e.mjs` observes it in a running WebView2, and nothing observes it in WebKitGTK or WKWebView.
- Nothing in `product/crates` sets `fullfsync`, so on macOS the durable claim has not been shown to survive power loss.
- On Windows the WebView2 profile is in `webview/` under the data directory, not the default location. WKWebView has no such setting, and wry ignores it there. On Linux an incognito window uses wry's own ephemeral context, while Tauri still creates a context on that directory. Run 42344969326, incognito with automation on, left `hsts-storage.sqlite`, `WebKitCache`, `mediakeys` and `storage/salt` there. What a shipped build writes has not been checked, and it bears on TA-20's WebView storage item.
- WebView2 can honour `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` in any build, as it did on a developer machine, so anyone who can set the user's environment could open a debugging port on the window. They already run as that user. It is noted here because no test covers it.
- On Linux, `TAURI_WEBVIEW_AUTOMATION=true` enables WebKit automation only in a build that is not incognito, which today means the `e2e` build. Run 42344969326 shows an incognito build refusing the session.
- On Linux, `tauri.linux.conf.json` names the keyring helper as an external binary, so every Linux build of the app copies it beside the executable, where the vault looks for it. The build needs `src-tauri/binaries/safeevidence-linux-keyring-helper-<target triple>` first. CI builds it, and on x86-64 Linux a developer runs, from `product/`:

  ```
  cargo build --locked -p safeevidence-linux-keyring-helper
  mkdir -p apps/desktop/src-tauri/binaries
  cp target/debug/safeevidence-linux-keyring-helper apps/desktop/src-tauri/binaries/safeevidence-linux-keyring-helper-x86_64-unknown-linux-gnu
  ```

  Copy it again after rebuilding the helper: the app's build only notices a change to the copied file, so an old copy stays beside the app. Bundles stay off, so no installer carries the helper yet. That waits for signed releases under EXT-05.
- **WebView storage**, checked before M1 exit as `plan-v1.5` asks: after the Ask flow and a restart, the end-to-end test scans every file in the web view's data directory for the answer, the cited span and the proof id, in UTF-8 and UTF-16LE. On Windows the shipped incognito window leaves none in about 130 files. The page writes nothing to web storage today, so this is a tripwire for future writes, not proof that incognito prevents them. Two one-off manual runs, not part of the test, showed more. With incognito on, a page writing the answer to `localStorage` and IndexedDB still left none on disk. With incognito off, the scan found it in WebView2's `Local Storage` LevelDB log. On Linux the test window is not incognito, so the check covers a configuration that does not ship, and it reads only the data directory, not WebKit's other cache or data folders. The scan misses compressed LevelDB blocks. The rest of TA-20's shell checklist (cache, crash dumps, clipboard) stays with M4.
- **No-socket capture evidence for VS-1a** (`plan-v1.1` §C), on Linux only. The end-to-end run starts the app under `strace -ff`, one file per process, so the app, the keyring helper and WebKit's web and network processes are traced across both launches. A CI step lists their internet-family socket, bind, listen, accept, connect and send calls, and any connect to a resolver's Unix socket, and prints each line. Runs 42407390348 (`f4e7600`) and 42409511656 (`89ad78f`) recorded no call outside loopback and no direct DNS. Each launch had one loopback port, used by the app and its web process, probably WebKit's automation channel for the test driver, which is unverified. This is evidence from a few runs, not a `NETWORK_LOCKED` run or a TA-21 pass. Its limits: strace sees system calls, not packets. Processes outside the traced tree, such as the D-Bus daemon and anything it starts, the keyring daemon and the system resolver, are not traced. io_uring is not traced. WebDriver automation is on and the window is not incognito, unlike what ships. The trace is printed in the CI log, which expires, and is not kept as an artifact. Windows and macOS have no capture.
