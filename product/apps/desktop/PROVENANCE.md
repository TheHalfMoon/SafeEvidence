# Provenance: SafeEvidence desktop shell

Admission `ADM-0006` (T36) in `docs/evidence/source_admissions.json`.

- Source: `AbdulazizShehri/MedScale` @ `5c33d77c0a82748c1fab85a9f2fd7b515145fea2`, `apps/desktop-tauri/`, Apache-2.0.
- Copied and reduced: the Tauri and Vite configuration, the capability and navigation discipline, the startup-failure path and the
  permission tests. MedScale's commands, routes, autogenerated permissions, brand assets and Tailwind are not copied.
- Tightened: `default-src 'none'` and no `'unsafe-inline'` in production, and bundling is off.
- Adapted from the donor's `src/ipc.ts` and `src/ipc.test.ts`: the reject-a-mismatched-protocol parser pattern in `src/ask-view.ts` and its test.
- SafeEvidence-written (GREENFIELD_JUSTIFIED, product-specific view; the shell is the copied part): the rest of `src/ask-view.ts`,
  `src/App.tsx`, `src/styles.css`, `src-tauri/src/ask_command.rs`. The icons are generated plain squares.

The Ask command commits through `safeevidence-proofstore` first, and shows the stored text only if the stored proof reads `COMMITTED`. No existing test tells that read from Ask's own text, because the commit binds the text's digest: a mutant that removes only the read passes every test.

## Limits

- **Key custody is on-device and has no recovery path.** The store's root key is held by the OS protector: DPAPI on Windows, Keychain on macOS, and Secret Service through the helper on Linux. Answers survive a restart. If the key is lost or wrong, the store is
  refused and its contents are kept, with no way to recover it yet. A refused open, with a wrong key or on a damaged main file, can still merge a live WAL into the main file, which changes the files. Backup, restore and rotation are not wired in. This holds invented data only.
- A store that was established and has lost or emptied its main file, or its schema, is refused, and so is a WAL with no main file, so none can be silently recreated. Removing the store directory by hand is the only way to start again.
- **Loss of the WAL can go unnoticed.** Once the main file holds a schema, a lost or damaged WAL looks like a clean store, so commits since the last checkpoint are forgotten with no warning, an invalidated answer could come back as an answer, and an old proof could read "Just committed" again. Telling them apart needs a protected anchor, which is not built. A kill alone is safe: this needs the WAL itself to be damaged.
- Each fixture digest has its own store directory, so a changed fixture starts a new store and the old one stays on disk, unused and never cleaned up.
- A crash during first install can leave a partial protector record or a `dpapi` directory with an inherited ACL. Those are refused until someone removes them by hand. A review measured this at 19 of 400 kills spread across the first open, of about 70 ms, on real DPAPI. No data is at stake in that state. A copied or restored `dpapi` directory is refused too, and no manual ACL repair has been established.
- Only Windows runs its real protector in the desktop tests. macOS has not been run through this path, and Linux reaches it only through the helper, whose real-provider tests are in its own crate. Nothing installs the helper beside the app, so on Linux the app refuses every question until
  `safeevidence-linux-keyring-helper` is placed next to its executable.
- The store has no migrations, so a schema change would refuse an existing store. `vault-identity.bin` is not secret and not protected: changing it only stops the key from being found.
- The P00 states such as `KEY_UNAVAILABLE` are not shown. Every failure to open the store reaches the view as the same `BLOCKED` with `TOOL_FAILURE`: a lost or wrong key, a damaged identity or store, a missing helper, and a second instance look alike.
- A lock file gives one running instance per data directory. A second instance refuses every question it would answer with `BLOCKED`.
- `TA-20` is not claimed. `e2e/ask_e2e.mjs` runs the Ask flow in a real WebView2 window, with real DPAPI and a real kill and restart, as the Ask subset. Run 42348262998 removed the CSP and granted `core:default`: all the CSP probes flipped and the refusal became "allowed". It places the helper beside the app itself, because nothing installs it yet. - **No-socket capture evidence for VS-1a** (`plan-v1.1` §C), on Linux only. The end-to-end run starts the app under `strace -ff`, one file per process, so the app, the keyring helper and WebKit's web and network processes are traced across both launches. A CI step lists their internet-family socket, bind, listen, accept, connect and send calls, and any connect to a resolver's Unix socket, and prints each line. Runs 42407390348 (`f4e7600`) and 42409511656 (`89ad78f`) recorded no call outside loopback and no direct DNS. Run 42410086920 (`e0ed6c8`), which also traces bind and listen, found the cause of the loopback connections: **on each launch the app binds a listening socket on loopback**, which the app and its web process then connect to. A build as it ships, with no `e2e` feature, so no WebDriver automation, and with incognito, showed no such listener in run 42414388764 (at `bf7e512`). Over 30 seconds of startup and idle, the app, WebKit's network process and its web process made no internet-family bind, connect or accept, and no send to an address. That is consistent with the listener coming from the automation setup, but does not show it. The bind is in the app's own process. The two runs also differ in incognito, the data directory, the keyring helper and asking questions, and the shipped-style run asked no question and was a debug build. Whether a shipped build opens a listener during an Ask is still owed before M1 exit. This is evidence from a few runs, not a `NETWORK_LOCKED` run or a TA-21 pass. Its limits: strace sees system calls, not packets. Processes outside the traced tree, such as the D-Bus daemon and anything it starts, the keyring daemon and the system resolver, are not traced. io_uring is not traced. WebDriver automation is on and the window is not incognito, unlike what ships. The trace is printed in the CI log, which expires, and is not kept as an artifact. Windows is in the next item.
- **No-socket capture evidence for VS-1a on Windows, test build: WebView2 connects outside loopback.** During the Windows end-to-end run a poller reads `netstat -ano` every few hundred milliseconds and keeps the sockets of the app and the WebView2 processes descended from it; the report fails unless it sees the test build's debugging listener on 9333. Run 42440486315 (`3236796`) saw a WebView2 process (`msedgewebview2.exe`) hold a TCP connection to 150.171.22.17 port 443, established in 5 samples and opening in 1. ARIN registers 150.171.0.0/16 to Microsoft. A third run, 42442779313 (`21fe1eb`), saw a connection to 52.123.250.172 port 443 (ARIN: 52.120.0.0 to 52.123.255.255, Microsoft) in 1 sample and a UDP socket bound outside loopback in 7, so the destination varies between runs. The earlier run 42438606924 (`bbd2846`) also saw a port 443 connection outside loopback in 3 samples, whose address that report did not print, and a UDP socket bound outside loopback. Which WebView2 or Edge service made the connection, and what it sent, is not known; none of these sockets were in the app's own process. This was the test build, with a debugging port and WebDriver-style automation, not a build as it ships. It is a privacy finding against TA-21's no-traffic claim, owed a fix or a founder ruling before M1 exit. Polling misses short-lived sockets, and DNS done by the Dnscache service is not attributed. A bound UDP socket shows no destination, so UDP traffic such as QUIC cannot be attributed to a host. A build as it ships, without the `e2e` feature and so without a debugging port, was captured over startup and 30 seconds idle in run 42450610768 (`a7c90b0`): in 192 samples with WebView2 in the app's tree, it held no TCP connection outside loopback, one loopback TCP connection to port 80 in 1 sample, also unexplained since the build serves its pages in-process, and a UDP socket bound on 0.0.0.0 port 51372 in 187. Whether that UDP socket sent anything, and where, netstat cannot show. No question was asked, it was an unsigned debug build, and one idle run of 30 seconds does not show the outside TCP connection never happens in a shipped build. The process tree is found by image name and parent PID, so an orphaned WebView2 process would be missed. macOS has no capture. **After WebView2 switches (run 42485847303, `0cc6f74`):** every Windows build now asks WebView2 to turn off its background services (see `main.rs`, `WEBVIEW2_ARGS`). In that run, the test build, through the whole Ask flow, held no socket outside loopback over 22 samples; the shipped-style build, over startup and 30 seconds idle, held none over 173 samples, and no UDP socket. Both held a loopback TCP connection to port 80: the test build in 7 of 22 samples, the shipped-style build in 172 of 173, against 1 of 192 before the switches, so the switches may have caused it. Run 42521709468 (`7744c20`) named the listener on port 80: the `System` process (PID 4), a kernel-mode owner, on port 80 normally the HTTP service HTTP.sys, not the app; whether HTTP.sys passes the connection to any registered handler is unknown; the test build held the connection in 7 of 23 samples and the shipped-style build in 177 of 177. The app's pages load from `http://tauri.localhost`, a loopback name on port 80 that WebView2 serves from inside the app, so one explanation is WebView2 opening a connection to that origin before serving the request itself. That is not shown: the capture sees the connection, not whether any bytes, such as a question, were sent over it. On a user's machine, whatever listens on loopback port 80 would receive the connection. Run 42530898719 (`ff9ad31`) then stopped the runner's HTTP service (which also stopped IIS's World Wide Web Publishing Service, so a web server was listening there before), listened on loopback port 80 itself without answering, and launched the shipped-style build for 30 seconds: one connection arrived, from `::1`, and **carried 0 bytes**, while a control request was recorded in full. That is consistent with WebView2 opening a connection to the pages' origin and then serving the request itself. Run 42537385684 (`aef7f4d`), with IPv4 and IPv6 controls both recorded, saw the same: one connection from `::1`, opened about 0.4 seconds after launch and held until the app was closed 30 seconds later, carrying 0 bytes. The listener does not record which process connected; the app's WebView2 is the likely source, since the netstat captures attribute a port 80 connection to it. Two runs, over startup and idle with no question asked, with a listener that never answers, which may differ from a listener that does. **During an Ask** (run 42555157901, `e6693a0`), the same listener ran while the end-to-end test asked its questions in the e2e build, across both launches, and all 12 checks passed: two connections from `::1` arrived, open 1.5 and 0.2 seconds, both carrying 0 bytes, and the test's typed nonce never reached the port. That is the e2e build, which has a debugging port, in one run. This is one run of each, with the same polling limits; switches are requests to WebView2, not a guarantee, and the WebView2 runtime's own updater runs outside the app's process tree.
